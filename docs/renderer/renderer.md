# renderer

Графический контекст, кадр и камера.

## Назначение

Подсистема владеет графическим API и отправляет кадры на устройство. Игровой код не знает, какой API выбран и как устроены его ресурсы.

## Публичный API

```cpp
struct Vector3 { float x, y, z; };

struct Camera {
    Vector3 position, target, up;
    float field_of_view;
    float near_plane, far_plane;
};

struct Vertex { float x, y, z; float u, v; };

class Renderer {
    void resize(std::uint32_t width, std::uint32_t height);

    void begin_frame(const Camera& camera);
    void draw(const Mesh& mesh, const Texture& texture, std::span<const float, 16> transform);
    void end_frame();
};

std::shared_ptr<Renderer> create_renderer(void* native_window_handle,
                                          std::uint32_t width, std::uint32_t height);

std::shared_ptr<Mesh> create_mesh(std::span<const Vertex> vertices,
                                  std::span<const std::uint16_t> indices);

std::shared_ptr<Texture> create_texture(std::uint16_t width, std::uint16_t height,
                                        std::span<const std::byte> pixels);
```

## Границы

Подсистема не создаёт окно и не обрабатывает события. Она принимает готовый хендл и размер кадрового буфера, см. [platform](../platform/window.md).

Подсистема не знает про сущности мира и не решает, что рисовать: вызывающий передаёт меш, текстуру и матрицу модели.

Подсистема не читает файлы. Геометрия и изображения поступают как данные в памяти.

## Состав

| Файл | Содержимое |
|---|---|
| `renderer.h` | контекст, кадр |
| `camera.h` | положение наблюдателя и проекция |
| `mesh.h` | вершина, буферы геометрии |
| `texture.h` | изображение на устройстве |
| `shaders/` | исходники шейдеров и описание varying |

## Решения

**Камера здесь, а не в подсистеме окна.** Положение наблюдателя и проекция — это матрицы вида и проекции, то есть рендеринг. Окно про них ничего не знает и знать не должно.

**Соотношение сторон не хранится.** Оно выводится из текущего размера кадрового буфера при построении матрицы проекции. Хранить его отдельно значило бы держать вторую копию того же факта.

**Хендл окна — `void*`.** Тип платформы не попадает ни сюда, ни в подсистему окна: он известен только реализациям обеих.

**Владение библиотекой — RAII.** `bgfx::init` и `bgfx::shutdown` парные и привязаны ко времени жизни отдельного типа, поэтому выключение не выполняется при неудавшейся инициализации.

**Одна область вывода.** Кадр очищается и предъявляется целиком. Разделение на проходы появится, когда появится что рисовать.

**Меш и текстура принимают данные, а не пути.** Подсистема загружает на устройство то, что ей передали, и не знает, откуда это взялось. Появление конвейера ассетов не затронет её интерфейс.

**Кадр открывается и закрывается явно.** `begin_frame` задаёт камеру, `draw` помещает меш, `end_frame` отправляет кадр. Один вызов на весь кадр пришлось бы переделывать при втором объекте в сцене.

Порядок вызовов не выражен в типах: `draw` вне кадра ошибочен, но компилятор этого не заметит. Ограничение принято сознательно, пока в кадре один объект.

**Шейдеры встроены в исполняемый файл.** `bgfx_compile_shaders` компилирует их при сборке в заголовки, по варианту на графический API. У клиента нет зависимости от расположения файлов; чтение с диска появится вместе с конвейером ассетов.

Профили ограничены Direct3D 11, Vulkan, OpenGL и OpenGL ES. Direct3D 12 (`s_6_0`) исключён: компилятор HLSL выдаёт предупреждение внутри собственного кода, а `shaderc` вызывается с `--Werror`. WebGPU в целевых платформах не значится.

## Зависимости

bgfx и bx, приватно. В публичном API их типов нет: заголовок оперирует `Camera` и `void*`.

## Замечание о размере

bgfx требует сообщать об изменении размера кадрового буфера отдельно: смена размера окна сама по себе его не меняет. Поэтому `resize` вызывается из главного цикла, когда окно сообщило о событии.
