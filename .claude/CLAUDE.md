# CLAUDE.md

Верхнеуровневые принципы работы над проектом.

`README.md` описывает **что** мы строим. Этот файл — **как** мы это делаем и что считаем неприемлемым.

При конфликте: README задаёт архитектуру и стек, CLAUDE.md — дисциплину. Правило, мешающее выполнить задачу, — повод остановиться и обсудить, а не обойти его.

---

## Главные принципы

### Чистота архитектуры важнее скорости получения результата

Код, который работает, но размывает границы подсистем, хуже отсутствующего кода. Отсутствующий код можно написать; размытые границы приходится вычищать из всего репозитория.

Если задача решается только ценой нарушения архитектуры — задача сформулирована неверно. Нужно сказать об этом, а не «сделать пока так».

### В документации нет лишних слов

Если слово можно убрать без утраты смысла — его убирают.

Это относится ко всему тексту в репозитории: README, CLAUDE.md, документам в `docs/`, комментариям, сообщениям коммитов, описаниям задач и ответам агента.

Убираем:

- вводные обороты: «стоит отметить», «как известно», «важно понимать»;
- усилители без содержания: «очень», «действительно», «крайне», «достаточно»;
- смягчители, скрывающие утверждение: «в целом», «как правило», «может быть», «скорее всего» — когда факт известен точно;
- пересказ уже сказанного другими словами;
- объяснение очевидного;
- фразы о структуре текста: «в этом разделе описано», «далее рассмотрим»;
- оговорки, ничего не меняющие для читателя.

Формулировки утвердительные: «мир — это данные ECS», а не «мир, как правило, представляет собой данные».

Точность важнее краткости. Слово, несущее смысл, не сокращают ради объёма: убирают лишнее, а не нужное.

Документ, который стал вдвое короче без потери содержания, стал вдвое лучше.

## 1. Изоляция подсистем

Каждая подсистема — это **чёрный ящик с лаконичным API**.

- Подсистема раскрывает минимум типов и функций, нужных её потребителям.
- Внутреннее устройство (структуры данных, аллокаторы, хендлы библиотек, кэши) наружу не протекает.
- Публичный заголовок не подключает заголовки сторонних библиотек. Тип из bgfx, SDL, Jolt в публичном API — ошибка, а не деталь.
- Направление зависимостей одностороннее: `game → runtime → engine → библиотеки`. Обратных стрелок не бывает. Ссылка на игровой тип в движке — ошибка.
- Подсистемы одного уровня не знают друг о друге напрямую. Связывает их слой выше.

Проверка перед добавлением сущности в публичный API:

> Если бы эту подсистему завтра переписали с нуля, поменялся бы этот интерфейс?
> Если да — это деталь реализации, ей не место в публичном API.

## 2. Никаких костылей

Костыль — это код, который работает не потому, что задача решена, а потому, что решение обошло проблему.

Признаки:

- «временно», «пока так», «потом переделаем» в комментарии;
- специальный случай для одного вызывающего;
- флаг в API, включающий другое поведение для конкретного потребителя;
- проверка типа/имени/индекса вместо нормальной абстракции;
- порядок вызовов, который нельзя менять, но нигде не выражен в типах.

Костыли не добавляем. Если правильное решение сейчас слишком дорого — останавливаемся и обсуждаем, а не оставляем обходной путь в коде.

Единственное исключение — обход **чужого** бага (библиотека, драйвер, платформа). Такой обход сопровождается комментарием с причиной, ссылкой и условием снятия.

## 3. Не строим впрок

Реализуем то, что нужно **сейчас**, и ничего больше.

- Никаких точек расширения «на будущее»: нет виртуальных функций без второй реализации, нет интерфейсов с одним наследником, нет плагинных механизмов без плагинов.
- Никаких шаблонов ради обобщённости, которая никем не используется.
- Никаких конфигурируемых параметров, которые всегда имеют одно значение.
- Абстракция появляется на **третьем** повторении, а не на первом и не в предвидении второго.

Убрать лишний слой позже стоит дороже, чем добавить нужный.

## 4. Не добавляем кэши

**Кэш существует только там, где без него не обойтись.** Кэш — это дублирование состояния и новый источник ошибок инвалидации. По умолчанию кэшей нет.

Кэш допустим, когда одновременно:

1. есть измеренная проблема производительности (профиль, а не догадка);
2. без кэша не обойтись: убрать саму работу или сделать её дешевле не вышло;
3. правило инвалидации формулируется одной фразой и очевидно полное.

То же касается любой производной информации: индексов, зеркальных карт, «удобных» копий данных рядом с оригиналом. Одна истина в одном месте.

Владение ресурсами — не кэш: asset manager хранит загруженное по своей задаче, а не ради ускорения.

## 5. Явное владение и время жизни

- У каждого ресурса ровно один владелец, и по коду видно, кто он.
- RAII везде. Освобождение вручную и парные `init`/`shutdown` в вызывающем коде — только там, где этого требует внешняя библиотека, и тогда обёрнутые в RAII-тип.
- Владеющий указатель — `std::shared_ptr`. Он принят как умный указатель по умолчанию ради простоты работы с forward declaration: полный тип не нужен ни владельцу, ни его деструктору.
- Данные в сырых указателях не хранятся. Сырой указатель — заимствование без владения, допустимое там, где значение может быть `nullptr`.
- Заимствование пережить владельца не может.
- Глобального изменяемого состояния нет. Синглтоны не создаём: зависимость передаётся явно.

### Передача аргументов

- По умолчанию передаём по ссылке: `const T&` для чтения, `T&` — когда функция изменяет аргумент.
- Сырой указатель в параметре означает «допустим `nullptr`». Другого повода передавать указатель нет.
- По значению передаём то, что дешевле скопировать, чем адресовать: скаляры, хендлы, небольшие тривиальные структуры.

### `std::move`

`std::move` — только там, где без него не обойтись: перемещение действительно требуется и копия неприемлема.

Не применяем:

- к возвращаемому значению локальной переменной — это ломает NRVO;
- ради «оптимизации» без измерения;
- к тому, что дальше используется, — источник остаётся в неопределённом состоянии.

### Forward declaration

Используем максимально широко.

- В заголовке подключаем только то, без чего он не компилируется. Всё остальное — `#include` в `.cpp`.
- Тип, используемый в заголовке как ссылка, указатель или `shared_ptr`, объявляем вперёд.
- Полное определение нужно заголовку, когда тип входит в него по значению, наследуется или требует размера.
- Публичный заголовок подсистемы объявляет вперёд собственные типы вместо подключения внутренних заголовков — см. раздел 1.

## 6. Данные важнее иерархий

- Наследование — только там, где нужен полиморфизм времени выполнения с несколькими реальными реализациями. Наследование ради переиспользования кода не применяем.
- Мир — это данные, а не граф объектов.
- Предпочитаем плоские непрерывные структуры разрозненным узлам со ссылками друг на друга.
- Поведение живёт в системах, состояние — в компонентах и структурах данных.

## 7. Производительность

- Не оптимизируем по предположениям — только по измерениям.
- Не создаём заведомо лишней работы: аллокации в кадровом цикле, копирования крупных данных, перевыделения контейнеров в горячем пути.
- «Не оптимизировать преждевременно» не оправдывает небрежность. Выбор структуры данных — проектирование, а не оптимизация.

## 8. Кроссплатформенность

- Платформенный код изолируется в `platform` и не расползается по остальным подсистемам.
- `#ifdef` по платформам в игровом и рантайм-коде не появляется.
- Не полагаемся на поведение конкретного компилятора, размер типа или порядок байт без явной проверки.

## 9. Размер и читаемость

- Модуль целиком помещается в голову — человеку и агенту.
- Файл, потерявший одну внятную ответственность, разделяем.
- Имена описывают назначение, а не реализацию. Сокращений избегаем.
- Комментарии объясняют **почему**, а не **что**. Код, требующий комментария «что он делает», переписываем.
- Мёртвый код удаляем, а не комментируем. История есть в git.

## 10. Документация и навигация по коду

Вся документация живёт в `docs/`.

```text
README.md                описание проекта
docs/
├── code_map.md          карта кода: подсистемы, расположение, зависимости
└── <subsystem>/*.md     описание конкретной подсистемы
.claude/
├── CLAUDE.md            правила работы (этот файл)
└── skills/              навыки агента
```

`README.md` описывает проект и лежит в корне. `.claude/CLAUDE.md` задаёт правила работы и лежит рядом с остальной конфигурацией агента: настройками и навыками.

### Навигация по коду

Порядок изучения кода — от карты к файлам, а не наоборот:

1. **`docs/code_map.md`** — определить, какая подсистема отвечает за задачу, где она лежит и от чего зависит.
2. **`docs/<subsystem>/`** — прочитать её описание: назначение, публичный API, границы, связи с соседями.
3. **Публичные заголовки** подсистемы (`include/`) — увидеть фактический интерфейс.
4. **Реализация** (`src/`) — только когда нужны детали.

Правила:

- Не начинаем работу с полнотекстового поиска по репозиторию: сначала карта.
- Расхождение документа с кодом — ошибка. Источник истины — код; документ правится в том же изменении.
- Не нашли подсистему в карте — она либо отсутствует, либо карта устарела. Оба случая обсуждаем, а не догадываемся.
- Перед созданием новой сущности проверяем по карте, нет ли существующей подсистемы с этой ответственностью.

### Обновление документации

Документация обновляется **в том же изменении, что и код**. Отдельной задачей «обновить документы потом» она не откладывается.

| Изменение в коде | Что правим |
| --- | --- |
| Новая подсистема | Строка в `code_map.md` + документ в `docs/<subsystem>/` |
| Изменился публичный API | Документ подсистемы |
| Изменились зависимости, назначение или расположение | `code_map.md` |
| Подсистема удалена | Строка в карте и её документы удаляются |
| Решение затрагивает несколько подсистем | Документ в `docs/` с обоснованием |

Документ подсистемы описывает: назначение, публичный API, границы ответственности, зависимости, принятые решения и их причины. Пересказ кода в него не переносится — код меняется чаще документа.

Требование «нет лишних слов» относится к документации в полной мере.

## 11. Дисциплина изменений

- Не трогаем то, о чём не просили. Попутный рефакторинг — отдельная задача.
- Публичный API не меняем молча: изменение сигнатуры или семантики называем явно.
- Зависимость не добавляем без обоснования: что она решает, почему не хватает своего кода, какова цена.
- Нетривиальная логика сопровождается тестом.
- Документация обновляется вместе с кодом — см. раздел 10.

## Стоп-сигналы

Останавливаемся и спрашиваем человека, если:

- задача требует нарушить направление зависимостей;
- нужен доступ к внутренностям чужой подсистемы;
- появляется желание добавить кэш, флаг, синглтон или «временное» решение;
- решение выглядит правильным, но требует переписать существующую подсистему;
- карта кода расходится с репозиторием;
- README не даёт ответа, а решение повлияет на архитектуру.

Такая остановка — не провал, а ожидаемая часть работы.

## Чек-лист перед завершением задачи

1. Границы подсистем не нарушены, направление зависимостей соблюдено.
2. Публичные заголовки не тянут за собой сторонние библиотеки.
3. Не добавлено ничего «на будущее».
4. Нет кэшей, дублирующего состояния и обходных путей.
5. Владение ресурсами явное, глобального изменяемого состояния нет.
6. `docs/code_map.md` и документы затронутых подсистем соответствуют коду.
7. Проект собирается; тесты проходят; предупреждений не добавилось.
8. Формат и статический анализ пройдены.
9. Изменения затрагивают только то, что относится к задаче.
